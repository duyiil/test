## 2. 演示脚本（正式演示约 10 分钟）

演示人：魏慧妍（主链路讲解）；如组内分工调整，每人负责段落在彩排时固定。
演示环境：本地一键启动 API + Worker + demo/sut + 前端（启动命令见 `docs/phase2.md`）；项目 Base URL `http://127.0.0.1:9000`（端口以彩排统一结果为准）。

| 时间 | 环节 | 操作 | 讲解要点（口径） |
| --- | --- | --- | --- |
| 0:00–0:30 | 开场 | 打开项目首页 | 一句话介绍：本轮演示 Sprint2 主链路"生成→审核→执行→报告"，生成是 Mock 版 |
| 0:30–1:30 | 项目与契约 | 打开测试项目，点击「载入演示契约」 | 契约写入项目，作为 Mock 生成依据；被测服务为 `demo/sut`（作者自建演示服务） |
| 1:30–3:00 | 生成 | 点击「生成测试草稿」，观察进度与待审区 | 强调：Mock 生成（AC-19 mock 口径）；生成结果一律草稿态（TC-TESTGEN-006） |
| 3:00–4:30 | 审核（1） | 驳回一条用例：先不填原因提交（看报错），再补原因提交 | 强调：驳回原因必填（TC-REVIEW-003）、草稿不能执行（AC-04 口径） |
| 4:30–5:30 | 审核（2） | 通过若干条用例，报出采纳率数字 | 采纳率 ≥ 60% 的迭代验收口径 |
| 5:30–7:00 | 执行 | 进入执行页：先展示写操作二次确认提示，确认后入队；观察执行进度与终态 | 强调：独立 Worker、4 类断言、写操作二次确认（未确认 409）；如演示同集并发冲突可加一句 409（TC-TESTRUN-018） |
| 7:00–8:30 | 执行明细 | 打开一条失败用例明细 | 展示完整请求/响应与断言逐项比对（期望值 vs 实际值）；指出这是 `demo/sut` 故意埋入的差异，不是环境故障 |
| 8:30–10:00 | 报告 | 打开数据报告 | 展示通过率、失败分布、耗时与环境信息；如实说明：AI 摘要当前 unavailable，报告降级为纯数据版，数据不丢（AC-21 口径） |
| 结束 | 收尾 | 回到追踪表 | 说明已完成口径与待办（做实模型、AI 研判等留待后续迭代） |

### 演示风险与预案

| 风险 | 预案 |
| --- | --- |
| 服务/进程未启动 | 演示前 10 分钟按 `docs/phase2.md` 清单逐个确认 API、Worker、demo/sut、前端四进程；截图留证 |
| 端口不一致（8001 vs 9000） | 彩排一之前统一并记录在《需求变更记录》CR-001，脚本与 Base URL 以统一后为准 |
| 现场误触发真实模型调用 | 默认不配置 `ZHITEST_LLM_API_KEY`，保持 Mock；不现场改配置 |
| AI 摘要 unavailable 被质疑 | 固定话术：AI 分析与数据报告分离，降级不丢数据，这是 AC-21 的设计要求，不是故障 |
| 执行失败过多画面难看 | 预先圈定演示用例集；失败明细正是演示点（断言逐项比对），按脚本引导讲解 |
